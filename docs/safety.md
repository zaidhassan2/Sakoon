# Safety implementation and review notes

Layer one normalizes every user message in the submitted window: Unicode decomposition, diacritic removal, zero-width removal, Arabic/Urdu yeh/kaf variants, punctuation, whitespace and repeated characters. English, Roman Urdu and Urdu phrase lists live in `lib/safety/phrases.js`. Direct/indirect intent, selected means, self-harm and immediate abuse cues trigger crisis. Hopelessness/trapped/exhaustion trigger elevated. A single explicitly negated, quoted, historical, or third-party crisis clause routes to elevated, never none. Multiple conflicting clauses remain conservative. “This deadline is killing me” does not alone trigger crisis. These rules are heuristic, not a clinical classifier; unseen euphemisms and transliterations can be missed.

Layer two asks the model for risk separately from its reply. The final risk can only rise above deterministic assessment, never fall. User content is never placed into a system role. Invalid JSON gets one extraction attempt, then sanitized raw-text handling for non-crisis, as specified. Blank/invalid reply fields use module fallback. Long verbatim instruction overlap and the explicit banned phrases also trigger fallback. These guards cannot guarantee protection against all prompt injection or unsafe clinical statements.

Layer three scans all user turns, ignoring assistant text for deterministic detection. Earlier crisis raises the current floor to elevated and adds the warm check-in system instruction. Three elevated user messages trigger crisis. The more specific cumulative API rule (elevated floor) is used even though the conversational prompt says to stay in crisis mode. Without a database or signed client state, risk cannot survive history omitted by the client, the twelve-message window, reloads, or model-only crisis decisions not reproduced in subsequent user text. Do not describe this as durable monitoring.

Crisis responses always use reviewed-in-code supportive templates after risk assessment, even when the model succeeds, ensuring no methods, helplines, links, or quick replies are emitted. Templates acknowledge pain, ask about current safety, encourage a real trusted person/help options/emergency services for immediate danger, and offer continued conversation. The owner-selected response language is Roman Urdu for all inputs; English and Urdu templates remain available in the source but are not selected at runtime; explicit English third-party wording selects an alternative template. They are seed translations awaiting native-speaker and clinician review, not clinically validated copy.

Detection runs before quota checks. A detected crisis returns 200 with source fallback when quota is exhausted, Redis fails, provider fails, times out, or emits malformed output. Unknown danger recognizable only by a model cannot be classified during provider outage. Invalid request bodies, disallowed origins and infrastructure rejections are not valid chat turns and are rejected. A user's client can drop history; the backend cannot infer it.

All output is plain text, capped at 140 words; markdown, URLs and phone-like digit sequences are removed, including Arabic-script digits. Quick replies are sanitized and limited to three, forty characters each; crisis replies have none. Phone/URL detection is lexical, so obfuscated/spelled-out contact details are not guaranteed to be caught. The backend provides no phone numbers, organisation directory or help links. The frontend owns those resources and needs independent verification.

Review before public use: ask a clinician and native Urdu speaker to extend phrase variants, test negation and third-party distinctions, evaluate templates and model replies across dialects, and assess model failure modes using the synthetic fixtures. Test separately with each provider/model. Automated tests establish software behaviour, not clinical safety or effectiveness.
